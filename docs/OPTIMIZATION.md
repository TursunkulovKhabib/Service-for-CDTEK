# Что оптимизируем при переносе на Python

Разбор по исходникам Java-сервиса. Слева — как сделано сейчас, справа — что
предлагается и что уже сделано.

## 1. Один хэш вместо множества проверок

**Было.** `UserServlet.doGet()` — `switch` на 700 строк: 16 веток (8 методов ×
числовой и строковый алиас), внутри каждой по 5–10 блоков
`try { x = Integer.parseInt(request.getParameter("limit")); } catch { x = 20; }`.
Один и тот же разбор `limit`, `page`, `min_digit`, `photo`, `empty` скопирован
четыре раза.

**Стало.** Действия разложены в словарь `{act: handler}` — поиск обработчика за
одно обращение вместо перебора веток. Разбор параметров вынесен в класс `Params`
(`text` / `flag` / `number` / `csv` / `date`): проверка написана один раз и
переиспользуется всеми методами. Обработка ошибок — один `try` на весь запрос,
формат ответа — `LegacyResponse`.

Файл: [employees/views/v1.py](../employees/views/v1.py).

## 2. SQL-запросы из UserService

**Было.** `getUserListByQRank` — строка SQL на 150 строк, собираемая
конкатенацией, с `CROSS JOIN words`, `GROUP BY` по 18 колонкам и постраничностью
через `rownum` в трёх вложенных подзапросах. Фильтры подставляются в текст
запроса: `" and org_id in ("+org_ids+") "` — **склейка значений прямо в SQL**.

**Стало / предлагается.**
* Ранжирование перенесено на ORM: одно `annotate` с суммой попаданий по словам,
  сортировка `-hits, full_name` — та же логика без `CROSS JOIN` и `GROUP BY`
  ([repositories/employee.py](../employees/repositories/employee.py), `search_rank`).
* Значения передаются параметрами — склейка в SQL исчезла как класс.
* Постраничность — `LIMIT/OFFSET` вместо тройной вложенности с `rownum`.
* Дальше: для больших объёмов заменить `LIKE '%...%'` на индекс `pg_trgm`
  (`GIN`) — это снимает full scan на поиске по подстроке.

## 3. Запросы к AD

**Было.** ФИО руководителя резолвится **отдельным запросом в AD на каждого
сотрудника** (`getUserByFilter` внутри цикла). На 3000 человек это 3000 лишних
обращений к контроллеру домена.

**Стало.** Руководители связываются одним вторым проходом по уже полученным
записям: `manager` — это DN, а DN у нас есть у всех загруженных сотрудников.
Ни одного дополнительного обращения к AD.

## 4. Полная выгрузка каждый час

**Было.** `LDAPTimerClass` раз в час гонит полную выгрузку всех доменов, затем
`saveUsers` построчно делает `select` + `update`/`insert` на каждого.

**Предлагается.** Инкрементальная выборка по `whenChanged` (уже реализована,
водяной знак хранится в журнале запусков) — полный обход остаётся только ночью.
Дальше: `bulk_update` пачками вместо построчных `UPDATE`.

## 5. Фото

**Было.** На каждой синхронизации `thumbnailPhoto` пережимается в два размера
(400×650 и 100×100) для **всех** сотрудников, независимо от того, менялось фото
или нет.

**Предлагается.** Хранить оригинал (уже так), пережимать лениво — при первом
запросе нужного размера, с кэшем; либо только при изменении `whenChanged`.
Отдавать фото отдельным URL, а не base64 внутри JSON: сейчас каждая выдача
списка тащит картинки в теле ответа.

## 6. Реквизиты доступа

**Было.** Логины и пароли AD, 1С ЗУП, 1С ДО — константами в `.java`; список
клиентов API с паролями — массивом `Object[] users` в `UserServlet`;
пароли к БД — в `context.xml`.

**Стало.** Всё в `.env`, который не попадает в git. Пароль LDAP в БД не хранится
— в карточке подключения лежит только имя переменной окружения. Клиенты API v1
задаются переменной `LEGACY_V1_CLIENTS`. В логах пароли маскируются фильтром.

## 7. Конфигурация под N компаний

**Было.** Блок из 15 переменных на компанию скопирован в `updateUsers()` дважды;
добавление третьей организации = правка кода и пересборка.

**Стало.** `COMPANY_CODES=cdtek;engs` в `.env` плюс блок переменных с префиксом
кода. Новая компания добавляется правкой `.env` и командой `load_companies` —
код не меняется. Подключения дальше правятся в админке.

## 8. Мелочи, которые стоит убрать при переносе

* `catch (Exception e) { e.printStackTrace(); }` — ошибка гасится, синхронизация
  продолжается с неполными данными. У нас прогон фиксируется в журнале со
  статусом и текстом ошибки.
* Замена `null` на `""` регулярками по готовой строке JSON
  (`jsonInString.replaceAll(":null", ":\"\"")`) — портит данные, где `null`
  встречается внутри текста. Сейчас пустые значения ставит сериализатор.
* `UserSessions` с пятью параллельными `HashMap` — заменяется сессиями Django.
* `ConnectionPool` с тремя почти одинаковыми наборами методов (MySQL / Oracle /
  Oracle DF) — Django ведёт пул сам.
